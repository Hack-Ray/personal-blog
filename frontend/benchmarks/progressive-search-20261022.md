# 1000 篇文章的漸進搜尋量測

> 2026-10-22 之後的變更：#55 不再產生舊版完整索引 `search-index.json`，內文分組也從 UTC 年份改為台北時間的年份。下文是量測當時（#53）的狀態，數字未重新量測。

2026-10-22。手機模擬下，標題結果的等待中位數由 **15.13 秒降至 1.16 秒，減少 92.3%**。最舊年份的內文命中等待未改善，這次中位數略長。改善來自先提供小索引；全部內文仍在背景下載。

每個情境各跑五次前後交錯比較，沒有失敗樣本或輸入重試。下表括號列出最小值至最大值。完整逐輪資料、查詢、命中文章、來源雜湊與傳輸檢查保存在 [量測資料](progressive-search-20261022.json)。

| 使用者等待的結果 | 舊版 | 漸進搜尋 |
|---|---:|---:|
| 從焦點啟動至標題結果出現 | 15.13 s（14.89–15.51） | 1.16 s（1.13–1.23） |
| 從焦點啟動至最舊年份的內文結果出現 | 15.08 s（14.78–16.46） | 16.71 s（16.35–17.96） |
| 標題情境的全部搜尋檔案下載完成 | 11.12 s（11.11–11.22） | 15.46 s（15.32–15.67） |

最舊內文情境的中位數差距與各輪變動範圍相近，不宣稱此項有改善。新版的全年份依序下載會增加請求與處理間隔，完整下載確實較晚完成。首批結果變快不能代表全文都已搜尋完。

新版標題情境中，畫面標示全文搜尋完成的中位數為 16.45 秒。這是新版獨有的 UI 狀態，沒有與舊版的資源下載時間混為同一項指標。

## 索引大小與行為

以下為實際匯出 JSON 的位元組數，gzip 使用 level 6。KB 與 MB 採十進位。

| 搜尋資料 | 原始 bytes | gzip bytes |
|---|---:|---:|
| 舊版完整索引 | 8,591,974 | 2,100,925 |
| 新版首份小索引 | 565,731 | 98,107 |
| 新版小索引加四個年份內文 | 9,015,863 | 2,118,083 |

首份索引的 gzip 大小減少 95.3%，全部搜尋資料的傳輸量增加 0.82%。新版保留舊版完整索引，供舊客戶端使用；新版介面不下載它，表中的新版總量也不包含它。

頁首取得焦點或進入搜尋頁時才開始下載。第一份索引包含所有已發布文章的標題、分類、標籤與 160 個 UTF-16 單位的搜尋文字。內文依 UTC 發布年份由新到舊下載，每年完成後自動更新篇數與排序。失敗時保留已有結果，重試從失敗年份接續。未操作的首頁與 404 頁不會下載搜尋索引。

完整搜尋維持原有的跨欄位 AND、子字串比對、標題／分類標籤／內文權重 10／5／1，以及同分日期排序。搜尋文字仍是摘要與去除 fenced code 後的內文合計前 5000 個 UTF-16 單位。短文字取自完整文字轉小寫後的前綴，載入年份內文時直接取代，避免重複計分。

## 查詢計算

Node 中以相同完整索引比較兩版搜尋函式。新版的預處理在計時前完成。先驗證 16 種查詢的文章順序與分數完全相同，再交錯跑五組、每組 100 次查詢，消耗命中與分數校驗值。

| 每次查詢的平均時間，再取五組中位數 | 舊版 | 預處理後 |
|---|---:|---:|
| Node 查詢計算 | 22.76 ms（21.92–27.64） | 1.74 ms（1.67–1.89） |

這項數字不包含下載、建立預處理資料或畫面更新。另一輪未計時報告的 CPU profile 顯示，舊版搜尋主要花在每次查詢都執行的內文 `toLowerCase()`；新版將文字正規化移出每次查詢。瀏覽器量測仍包含實際傳輸與畫面顯示，避免只以函式時間推論使用體驗。

## 條件與限制

- 舊版為 `a59075d5a4a7d35332e29c00271b93cc8bb5542c`，兩版使用相同依賴與相同的 1000 篇資料，均為正式靜態匯出。
- 固定資料雜湊為 `69b0d797a8cf3e2789699ee8822714f1eba5407faffad440bde7c8d7d79acb8e`。包含 20 個主題、60 個標籤、2023 至 2026 年，文章長度最小 1531、中位數 4756、最大 8463 字元，沒有圖片。
- 內容重複抽取 repo 的中文段落，壓縮會比彼此獨立的真實文章好。不能直接與先前隨機中文字的 29.5 秒報告相比。
- Node 22.22.0、Playwright 1.64.1、Chromium headless shell 141.0.7390.37，Linux x64、9 個邏輯 CPU。起始 load average 為 0.83／1.28／1.33，量測期間沒有同時建置或執行 CPU profile。
- 390×844、下載 1.6 Mbps、上傳 750 Kbps、延遲 150 ms、CPU 降速四倍。每輪新建瀏覽器 context，禁用快取與 service worker，檢查焦點前沒有搜尋請求。
- 計時前先等頁面 network idle、一次 browser idle callback 與兩個繪製 frame。這是**頁面已可互動、搜尋索引尚未載入**的量測，排除頁面載入與 hydration 初始階段。
- 計時從搜尋框取得焦點前開始，使用 `fill` 提交完整中文詞組，直到完整查詢與預期文章同時出現在下拉結果。這不是真實手機輸入法的組字測試，也不是逐字延遲。
- 早期探索在頁面初始化期間曾遺失或清空輸入，完整查詢檢查拒絕了那些樣本。最後這組 20 次量測由修正後的固定條件重新開始，沒有混入舊樣本、修補查詢或跳過失敗輪次。初始化時的輸入問題不在這份延遲改善結論內。
- 本機 HTTP/1.1 與 gzip 不包含 CDN、DNS、TLS、HTTP/2 或 Brotli；桌面 Chromium 的手機模擬也不等於實體手機。

舊版 2,100,925 bytes 在 200,000 bytes/s 下，純資料傳送下限約 10.50 秒；實際該檔傳輸約 11.08 秒，確認網路是首次搜尋的主要等待來源。新版首份索引的純傳送下限約 0.49 秒。其餘時間包含請求、瀏覽器處理與呈現；這份測試沒有將剩餘時間逐項拆成因果比例。分年下載的實際請求時間戳也顯示年份之間有處理間隔，不能用總 bytes 除頻寬預言全文完成時間。

## 驗證與重跑

單元測試 116 項、瀏覽器測試 20 項、型別檢查與五項量測工具檢查通過。CI 相同的示範站檢查通過。1000 篇、空文章、預設子路徑與網域根目錄的匯出，以及實際瀏覽器搜尋通過。瀏覽器案例涵蓋延遲年份、自動更新、重新排序、失敗重試、共用下載、查詢同步與首頁／404 不預載。

依照 [重跑說明](../scripts/bench-search-README.md) 產生一次固定資料，再分別建置兩個版本。使用 `--input-mode fill --trials 5`，讓兩版採用相同互動方式。完整計時資料可由工具重新產生；本頁連結的 JSON 保留每一輪的查詢與傳輸證據，省略大量非搜尋資源事件。探索失敗的資料沒有用來產生本頁的統計。
